DFS patterns reference

Three questions, six shapes. Walk the flowchart, find the shape, write the skeleton.

Every DFS problem reduces to three questions. Answer them in order and the algorithm falls out.

If Q1 lands you on backtracking, there's a fourth question for how each level branches — covered in the Branching styles tab.

How to use this

When you see a new problem, work through these three questions out loud (or in your head). The answers determine your code skeleton before you write a single line.

Worked example — the menu problem.
Q1: Building decisions (which entries to include) → backtracking.
Q2: All combinations achieving minimum cost → Shape F.
Q3: Path-dependent (cost + partial combo) → no memoization, add pruning.
Branching: Order doesn't matter, each entry used at most once → binary include/exclude (Style 2).
Result: backtracking with running best, result accumulator, cost-based prune, take/skip branching.
Worked example — LC 638 Shopping Offers.
Q1: Building decisions (which offers to apply) → backtracking.
Q2: Minimum cost only, single number → Shape E.
Q3: Path-independent (cost from remaining-counts doesn't depend on history) → memoize on count tuple.
Branching: Offers can be applied unlimited times → for-each-choice (Style 1) over offers at each state.
Result: top-down DP with memoization, no all-optima tracking.
The trap to avoid: Pattern-matching problem titles to memorized solutions. The framework forces you to derive the algorithm from structure, not from recall. That's what senior interviewers probe.

The first fork is about whether the search structure exists before you start. This determines whether you need an undo step.

Explicit structure

What it means

The graph, tree, or grid you're walking exists in memory. You traverse through it. Moving to a neighbor doesn't change the structure — there's nothing to undo.

Telltale signs

The input is a List[List[int]] grid, a TreeNode root, an adjacency list, or a Node with .neighbors. You're given the structure and asked to inspect or traverse it.

Code shape

def dfs(node, visited):
    if node in visited: return
    visited.add(node)
    for neighbor in node.neighbors:
        dfs(neighbor, visited)

Implicit structure

What it means

The "tree" is conceptual — each node is a state in a decision space, each edge is a choice. You build it as you walk. Trying a different choice means undoing the current one first.

Telltale signs

Input is a plain array, string, or set of items. The question asks you to choose, place, partition, or combine. No graph is given.

Code shape

def dfs(i, state):
    if goal(state): record(state); return
    if i == n: return
    for choice in choices(i):
        apply(choice)
        dfs(i + 1, new_state)
        undo(choice)   # <-- the key step

Example problems

LC 78Subsets LC 46Permutations LC 51N-Queens LC 37Sudoku Solver LC 39Combination Sum LC 22Generate Parentheses
The undo step is the giveaway. If you find yourself writing state.append(x) ... state.pop() around a recursive call, you're doing backtracking on an implicit structure. If you're not — if you just walk neighbors and mark visited — you're doing graph DFS on an explicit structure.

Hybrid cases

Some problems blur the line. LC 79 Word Search (find a word in a grid) walks an explicit grid but uses backtracking-with-undo because cells get marked-unmarked as you try different paths. The grid is explicit; the search through it builds an implicit decision tree. In these cases, you typically need both patterns: walk the explicit structure, undo the markings as you backtrack.

Once you're doing backtracking on an implicit structure, there's a second decision: how does each recursion level branch? Three styles cover almost every backtracking problem. Picking the right one is what prevents duplicate-output bugs.

The central question: Does order matter in the output? If yes → for-each-choice. If no → binary include/exclude or for-each-from-start. This single question determines your branching style.
Style 1 For-each-choice (positions × values)

Each recursion level represents a position to fill. Children fan out over candidate values. Use when order matters in the output.

Skeleton
def dfs(position, state, path):
    if position == n:
        results.append(path[:])
        return
    for value in valid_values(position, state):
        apply(position, value)
        path.append(value)
        dfs(position + 1, state, path)
        path.pop()
        undo(position, value)
Mental model

"I have N positions. For position 0, try each valid value. For position 1, try each valid value. ..." The branching factor at each level = number of values, depth = N positions.

Example problems
LC 46Permutations LC 47Permutations II LC 51N-Queens LC 37Sudoku Solver LC 22Generate Parentheses LC 17Letter Combinations of Phone Number LC 79Word Search
Style 2 Binary include / exclude

Each recursion level represents one item to decide on. Exactly two children: "with this item" and "without this item." Use when order doesn't matter and each item is used at most once.

Skeleton
def dfs(i, state, path):
    if goal_or_base_case:
        record(path)
        return
    if i == n: return

    # Include item i
    path.append(items[i])
    dfs(i + 1, new_state, path)
    path.pop()

    # Exclude item i
    dfs(i + 1, state, path)
Mental model

"For each item in order, decide yes or no." Branching factor = 2, depth = N items. The fixed iteration order is what prevents duplicate outputs like [1,2] and [2,1].

Example problems
The menu problem LC 416Partition Equal Subset Sum LC 494Target Sum 0/1 Knapsack Subset Sum variants
Style 3 For-each from start index

Like binary include/exclude, but expressed as a loop over remaining items. Each recursive call considers items from a start index onward. Use for subsets and combinations.

Skeleton
def dfs(start, path):
    record(path)   # every node may be valid
    for i in range(start, n):
        path.append(items[i])
        dfs(i + 1, path)   # i + 1 = no reuse
        path.pop()
        # For "with replacement" (LC 39), use dfs(i, path)
Mental model

"Walk forward through items in order. At each step, pick this item and continue, or skip it." Same outputs as binary include/exclude but the tree shape differs. The start parameter prevents revisiting earlier items, ensuring no duplicates.

Example problems
LC 78Subsets LC 77Combinations LC 39Combination Sum (with replacement: i not i+1) LC 40Combination Sum II LC 131Palindrome Partitioning LC 216Combination Sum III

Style 2 vs Style 3: are they the same?

They produce identical answer sets for subset-style problems but explore the tree differently:

Style 2 tree (binary)

For items=[A,B,C]: every internal node has exactly 2 children. Depth always 3. Total leaves = 2³ = 8 (one per subset, including empty).

Cleaner when you have a clear "decide each item" framing — like the menu problem deciding whether to include each entry.

Style 3 tree (start-index loop)

For items=[A,B,C]: branching factor decreases as you go deeper (3 at top, then 2, then 1). Each node is a valid subset, not just leaves.

Cleaner when every prefix path is a valid answer — like LC 78 Subsets where you record at every node.

Pick whichever feels more natural for the specific problem. They're equivalent in correctness. Style 2 reads "decide yes/no for each," Style 3 reads "walk forward picking what to add." Most people develop a preference.

Decision rule

QuestionAnswerStyle
Does order matter in the output? [1,2] ≠ [2,1] Yes Style 1 (for-each-choice)
Order doesn't matter, each item used at most once — Style 2 or 3
Each item can be used multiple times (with replacement) — Style 3 with i not i+1
Filling N fixed positions with constrained values — Style 1
Walking a grid/graph and choosing neighbors — Style 1 over neighbor list

Worked example — the menu problem

Walk the decision: does order matter? No — ["3","4","7"] and ["7","4","3"] are the same combination. Are items used at most once? Yes — you don't order the same menu entry twice. So Style 2 (binary include/exclude) or Style 3 (for-each-from-start) both apply.

The solution we wrote uses Style 2: for each entry, decide take or skip. That framing matches the problem language ("which entries do I include?") and produces exactly one path per combination, no deduplication needed.

What goes wrong if you pick the wrong style. If you used Style 1 (for-each-choice) on the menu problem — "for entry in entries: take it and recurse on remaining" — you'd generate [3,4,7] and [4,3,7] and [7,3,4] ... as separate branches, then your output would contain 6 copies of every 3-element combination. You'd then need to deduplicate by sorting and using a set of tuples. Wasted work. Style 2 sidesteps this by construction.

Once you know whether you're traversing explicit or implicit structure, the output shape determines your code skeleton. These six cover almost everything.

Shape A Boolean — does it exist?

Return True as soon as any branch finds a valid solution. Short-circuits the entire search.

Skeleton
def dfs(state) -> bool:
    if is_goal(state): return True
    if is_dead_end(state): return False
    for choice in choices(state):
        if dfs(next_state(state, choice)):
            return True   # short-circuit
    return False
Example problems
LC 416Partition Equal Subset Sum LC 79Word Search LC 207Course Schedule (cycle exists?) LC 282Expression Add Operators (reach target?) LC 980Unique Paths III variant (path exists?)
Shape B Count — how many?

Accumulate a count from subtrees. Each branch contributes a number; sum them up. No short-circuit.

Skeleton
def dfs(state) -> int:
    if is_goal(state): return 1
    if is_dead_end(state): return 0
    total = 0
    for choice in choices(state):
        total += dfs(next_state(state, choice))
    return total
Example problems
LC 200Number of Islands LC 91Decode Ways LC 70Climbing Stairs LC 62Unique Paths LC 377Combination Sum IV
Shape B problems are memoization magnets. The count from a given state is path-independent, so memoization usually applies — turning the DFS into top-down DP.
Shape C One example — find any solution

Carry the path/state with you. When you hit a goal, return it. First success bubbles up; failure tries the next branch.

Skeleton
def dfs(state, path) -> list | None:
    if is_goal(state): return path[:]
    if is_dead_end(state): return None
    for choice in choices(state):
        path.append(choice)
        result = dfs(next_state(state, choice), path)
        if result is not None:
            return result   # short-circuit
        path.pop()
    return None
Example problems
LC 37Sudoku Solver LC 51N-Queens (one solution variant) LC 139Word Break (any valid) LC 332Reconstruct Itinerary
Shape D All solutions — enumerate every valid

No short-circuit. Append every successful path to an outer result list. Exhaust the entire search space.

Skeleton
results = []

def dfs(state, path):
    if is_goal(state):
        results.append(path[:])
        return
    if is_dead_end(state): return
    for choice in choices(state):
        path.append(choice)
        dfs(next_state(state, choice), path)
        path.pop()
Example problems
LC 78Subsets LC 46Permutations LC 39Combination Sum LC 22Generate Parentheses LC 140Word Break II LC 797All Paths From Source to Target LC 51N-Queens
Path-dependence trap. The path argument is path-dependent state — different histories produce different paths. That means memoization on state alone doesn't work for collecting paths. You can memoize partial answers (e.g., LC 140 memoizes "all decompositions of suffix from i"), but it's not free.
Shape E Single optimum — find the best value

Track a running best. Prune branches that can't beat it. Often becomes top-down DP if state is path-independent.

Skeleton
best = float('inf')

def dfs(state, cost):
    nonlocal best
    if cost >= best: return   # prune
    if is_goal(state):
        best = min(best, cost)
        return
    for choice in choices(state):
        dfs(next_state(state, choice),
            cost + cost_of(choice))
Example problems
LC 638Shopping Offers LC 64Minimum Path Sum LC 322Coin Change (min coins) LC 787Cheapest Flights Within K Stops LC 174Dungeon Game
Shape F All optima — every solution at the best value

The hardest shape. Track best-so-far AND a result list. When a strictly better solution is found, reset the list. When equal, append. No short-circuit.

Skeleton
best_cost = float('inf')
best_solutions = []
EPS = 1e-6

def dfs(state, cost, path):
    nonlocal best_cost, best_solutions
    if cost > best_cost + EPS: return   # prune
    if is_goal(state):
        if cost < best_cost - EPS:
            best_cost = cost
            best_solutions = [path[:]]   # reset
        elif abs(cost - best_cost) < EPS:
            best_solutions.append(path[:])
        return
    for choice in choices(state):
        path.append(choice)
        dfs(next_state(state, choice),
            cost + cost_of(choice), path)
        path.pop()
Example problems
The menu problem LC 126Word Ladder II All shortest paths in a weighted graph All maximum-profit job schedules
Three pitfalls: (1) Using <= instead of strict < when checking "strictly better" — clobbers the equal-cost results. (2) Forgetting epsilon for floats. (3) Trying to memoize naively — but the path is path-dependent, so memoizing doesn't trivially work. LC 126 uses a clever BFS-then-DFS hybrid to manage this.

For rapid pattern-matching during practice. When you see a problem, scan these and find the closest fit.

By output keyword

A"is there", "can we", "does"

Boolean. Short-circuit on first success. Return up the stack.

B"how many ways", "number of"

Count. Sum from subtrees. Strong memoization candidate.

C"find a", "find any"

One example. Carry path, return it on success.

D"find all", "return all", "list all"

All solutions. Outer accumulator. No short-circuit.

E"minimum", "maximum", "best"

Single optimum. Running best + prune.

F"all minimum", "all shortest", "every optimal"

All optima. Running best + reset-on-better, append-on-equal.

By input shape

Grid / matrix

Explicit. DFS through cells. Common: islands, paths, flood fill.

Tree / linked structure

Explicit. Recurse on children. Common: path sums, tree validations.

Adjacency list / graph

Explicit. Track visited. Common: connectivity, cycles, topo sort.

Array of items to choose from

Implicit. Backtracking with take/skip. Common: subsets, combinations.

String to partition / decode

Implicit. Position-based recursion on suffixes. Memoization usually wins.

Board / grid to fill

Implicit. Position-based with constraint checks. N-Queens / Sudoku family.

Drills to internalize this

Drill 1. For every DFS problem you solve, label it: which shape (A-F), which structure (explicit/implicit), what's the state, is it path-independent. Write the label as a comment at the top of your solution.
Drill 2. Before reading a solution to a new problem, predict the shape and write the skeleton. Then compare to the actual solution. Track where your predictions are wrong.
Drill 3. After 30-50 problems, build your own pattern catalog. One line per problem: "Subsets — implicit, Shape D, state is (index, path), no memo, no prune." The catalog is more useful than any external resource because it's in your own framing.

Pattern recognition compounds. Volume + labelling + reflection > memorization.
